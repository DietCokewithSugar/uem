# 优化建议（平台核心功能）业务说明 · 演示版理解

本文整理演示版对「优化建议」的理解，作为后续核对与智能化重构的基础。
标记说明：**【确认】**来自你提供的流程图或截图；**【推测】**是演示版的补全，需要你确认或纠正。

## 1. 定位

优化建议是平台的核心闭环（【推测】，待你补充业务价值）：

1. 把客户和员工反馈的体验问题集中收集起来。
2. 按产品自动路由到业务研发中心各产品线。
3. 由产品经理明确是否采纳及解决方式。
4. 跟踪直到问题落实。

管理层通过管理报表和数据看板查看处理进展与成效。

## 3. 流程与状态

### 3.1 两条处理路径【确认】

- **研发一体化问题**：由软件开发中心处理，直接进入 e键通。
- **非研发一体化问题**：由业务研发中心产品经理处理，依次经过 分拣 → 答复 → 审核 → 跟进 → 完成。

### 3.2 答复环节决定后续去向【确认】

答复环节明确是否采纳及解决方式：

| 解决方式 | 审核通过后 |
| --- | --- |
| 不采纳 | 已完成 |
| 科技自主解决 | 转 e键通跟进解决，同步问题解决情况 → 待开发中心处理 → 已完成 |
| 业务科技协同解决（需求整合） | 同步 BRDM，纳入需求整合问题管理 → 已纳入需求整合池 |
| 业务科技协同解决（需求项） | 跟踪需求编写及需求项投产直至解决闭环 → 待跟进 → 已完成 |
| 业务科技协同解决（创意需求） | 同步工银e企创，纳入创意管理 → 已纳入e企创 |
| 业务自主解决 | 支持线上转总行业务部门处理闭环 → 待跟进 → 已完成 |

答复环节还支持线上转总行业务部门分析处理，进入「待业务部门答复」。

### 3.3 状态、处理岗与操作

| 状态 | 当前处理岗 | 可执行操作（演示版） | 依据 |
| --- | --- | --- | --- |
| 待修改 | 提交人 | 修改并重新提交 | 待办菜单【确认】，操作【推测】 |
| 待处理 | 分行科技审核岗 | 转处理（→ 待分拣）、中止、删除、退回提交人 | 待办菜单与批量按钮【确认】；由分行科技审核岗处理【推测】 |
| 待分拣 | 产品线分拣岗 | 指派答复人、转 e键通、退回提交人 | 详情页日志「指派答复人」【确认】 |
| 待答复 | 产品线处理岗 | 答复（采纳结果 / 解决方式 / 答复意见 / 优先级 / 需求项编号 / 计划落实时间）、转总行业务部门 | 日志「答复」备注格式【确认】 |
| 待审核 | 产品线审核岗（要客建议：产品线审核岗（要客）） | 通过、退回 | 日志「通过」、管理报表「待审核数」【确认】；待办中的入口【推测】 |
| 待跟进 | 产品线处理岗 | 跟进（是否已落实、实际落实时间） | 详情页字段【确认】 |
| 待业务部门答复 | 总行业务部门处理岗 | 业务部门答复（业务自主解决 / 业务不采纳） | 管理报表列【确认】，操作【推测】 |
| 待开发中心处理 | 软件开发中心（e键通） | 由 e键通同步处理完成或退回 | 管理报表列、「e键通退回明细」【确认】 |
| 已完成 / 已纳入需求整合池 / 已纳入e企创 / 已中止 | — | 提交人满意度评价【推测】 | 管理报表列、「答复满意度」页签【确认】 |

真实详情页日志的顺序（人员已替换为虚构）：

1. 提交
2. 分拣岗「指派答复人」
3. 处理岗「答复」，备注：`采纳结果:采纳；解决方式:业务科技协同解决（需求项）；答复意见:采纳；优先级:三级（非常用功能影响中等或小）；需求项编号:I20260814-0196；计划落实时间:2026-10-17；`
4. 「通过」，备注：`需求项编号：I20260814-0196,已联动BRDM。`
5. 状态变为「待跟进」

示例中，指派答复人和审核通过是同一人完成的。演示版因此让每条产品线的分拣岗兼任审核岗。

## 4. 路由规则【推测，依据产品维护与人员维护的字段】

1. **确定处理部门**：取「产品名称」在产品维护中的所属业研部门和所属业研产品线。如果产品没有业研部门、外部机构为「软件开发中心」，则视为研发一体化问题。
2. **分配处理人**：按人员维护中岗位的数据范围（产品线）找到分拣岗、处理岗、审核岗。
3. **要客建议**：来源为「客户：要客意见」或提出人带要客标记时，由「产品线审核岗（要客）」按业研部门审核。
4. **分行提交**：先经分行科技审核岗（待处理），再转处理进入分拣。

## 5. 新增表单【确认】

**字段顺序**（* 为必填）：

1. *描述及解决建议
2. *来源
3. 关联体验活动
4. *产品名称
5. *产品使用渠道
6. 功能栏目
7. *影响程度
8. *优化建议分类
9. 上传附件
10. 提交按钮

**字段细节**：

- **描述及解决建议**：按【现象】【建议】示例填写，严禁含客户隐私。旁边有「点我查询相似优化建议」链接。
- **产品使用渠道**：多选，按以下分组：
  - 手机APP：个人手机银行、企业手机银行、工银e生活、商户之家、数字货币、境外个人手机银行、工银e办公、兴农通
  - 电脑端：个人网上银行、企业网上银行、工银e办公
  - 微信：微信小程序、微信公众号/服务号
  - 线下：智能柜员机、柜面、POS、ATM
  - 其他：短信银行、电话银行、第三方渠道、行内系统/产品
- **上传附件**：最多 9 张图片，支持截图粘贴。

**选项取值**：

| 字段 | 取值 | 依据 |
| --- | --- | --- |
| 优化建议分类 | 功能流程、系统性能、交互设计、信息认知、视觉设计、运营服务、智能化、安全感知 | 数据看板图例【确认】；各分类说明【推测】 |
| 影响程度 | 大 / 中 / 小 | 「小（该问题对用户操作影响较小，但影响用户使用感受）」【确认】，大、中的说明【推测】 |
| 优先级 | 一级 / 二级 / 三级 | 「三级（非常用功能影响中等或小）」【确认】；一级、二级按「常用 / 非常用 × 影响大 / 中等或小」【推测】 |
| 未采纳原因 | — | 选项【推测】，看板有「未采纳原因分布情况」 |

## 6. 详情页【确认】

## 9. 与其他模块的联动

- **产品维护**：产品 → 业研部门 / 产品线 / 业务部门 / 外部机构，决定路由与研发一体化判定。
- **人员维护**：岗位及数据范围决定由谁处理（分拣岗、处理岗、审核岗、要客审核岗、总行业务部门处理岗、分行科技审核岗）。
- **节假日**：停留时长、逾期、平均处理时长都按工作日计算。
- **定时任务与邮件记录**：「优化建议待办提醒邮件」在工作日给当前处理人发 dealSuggestion 提醒。
- **体验问题维护**：
  - 「相似度」开启时，提交前提示相似建议。
  - 「沟通业务部门」开启时，答复环节可转总行业务部门【推测】。
- **字典维护**：来源、分类、影响程度、渠道、解决方式、优先级、未采纳原因可在字典中维护。
- **用户声音**：声音看板「转优化建议」生成一条优化建议，进入分拣。

## 11. 智能化重构的初步切入点（供讨论）

| 环节 | 思路 |
| --- | --- |
| 提交 | 描述质量检查（缺少现象或建议时提示补充）、隐私信息识别与脱敏、按描述自动推荐产品 / 渠道 / 分类 / 影响程度 |
| 查重 | 用语义相似度替代字面相似，合并重复建议并关联到已有处理结果 |
| 分拣 | 根据历史分拣记录推荐答复人；识别研发一体化问题并直接转 e键通 |
| 答复 | 参考同类建议的历史答复，生成答复草稿、推荐解决方式与优先级 |
| 跟进 | 预测逾期风险，提前提醒；自动同步 BRDM / e键通 状态 |
| 管理 | 看板、报表自动生成解读，按产品聚合典型问题（与用户声音的典型问题提炼打通） |
