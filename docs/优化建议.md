# 优化建议（平台核心功能）业务说明 · 演示版理解

本文整理「优化建议」的业务规则。声音流水线见《用户声音分析智能体》，旅程步骤见《灵犀旅程》。
标记说明：**【确认】**来自你提供的流程图、截图或后续讨论；**【待定】**是图上对不上、或这次还没定下来的点；**【推测】**仍是演示版自己的补全。

## 1. 定位

【确认，来自「1.1 优化建议整体流程」】优化建议是指在产品日常运营阶段，总分行人员主动开展用户体验评估，以及通过对各渠道、各种类用户声音归集、整理和分析后，形成的有助于提升用户体验感受的意见或建议。业务研发中心通过用户体验管理平台，对各渠道收集到的优化建议做全流程管理。

处理顺序见第 3、4 节。管理层通过管理报表和数据看板查看进展。

## 3. 流程与状态

### 3.1 两条处理路径【确认】

- **研发一体化问题**：提交时就进入 e键通，由软件开发中心处理，不先到产品部门的分拣岗【确认】。分行员工提交的先经分行审批，见第 4 节。
- **非研发一体化问题**：由业务研发中心产品经理处理，依次经过 分拣 → 答复 → 审核 → 跟进 → 完成【确认】。分拣、答复、审核由三个独立岗位完成，见第 4 节。

### 3.2 答复环节决定后续去向【确认】

答复环节明确是否采纳及解决方式：

| 解决方式 | 审核通过后 |
| --- | --- |
| 不采纳 | 审核通过后提交人可见处理情况。是否随即变为「已完成」见第 4 节【待定】 |
| 科技自主解决 | 转 e键通跟进解决，同步问题解决情况 → 待开发中心处理 → 已完成 |
| 业务科技协同解决（需求整合） | 同步 BRDM，纳入需求整合问题管理 → 已纳入需求整合池 |
| 业务科技协同解决（需求项） | 跟踪需求编写及需求项投产直至解决闭环 → 待跟进 → 已完成 |
| 业务科技协同解决（创意需求） | 同步工银e企创，纳入创意管理 → 已纳入e企创 |
| 业务自主解决 | 支持线上转总行业务部门处理闭环 → 待跟进 → 已完成 |

答复环节还支持线上转总行业务部门分析处理，进入「待业务部门答复」。

### 3.3 状态、处理岗与操作

| 状态 | 当前处理岗 | 可执行操作（演示版） | 依据 |
| --- | --- | --- | --- |
| 待修改 | 提交人 | 修改并重新提交 | 待办菜单【确认】，操作【推测】 |
| 待审批（原「待处理」） | 分行科技审核岗 | 审批通过（→ 按产品分类自动分配，见第 4 节）、中止、删除、退回提交人 | 待办菜单与批量按钮【确认】；分行员工提交时由本行分行科技审核岗审批【确认】 |
| 待分拣 | 产品线分拣岗 | 指派答复人、转 e键通、退回提交人 | 详情页日志「指派答复人」【确认】 |
| 待答复 | 产品线处理岗（答复人） | 答复（采纳结果 / 解决方式 / 答复意见 / 优先级 / 需求项编号 / 计划落实时间）、转总行业务部门、退回提出人 | 答复备注格式【确认】；退回提出人【确认】 |

| 待跟进 | 产品线处理岗 | 跟进（是否已落实、实际落实时间） | 详情页字段【确认】 |
| 待业务部门答复 | 总行业务部门处理岗 | 业务部门答复（业务自主解决 / 业务不采纳） | 管理报表列【确认】，操作【推测】 |
| 待开发中心处理 | 软件开发中心（e键通） | 由 e键通同步处理完成或退回 | 管理报表列、「e键通退回明细」【确认】 |
| 已完成 / 已纳入需求整合池 / 已纳入e企创 / 已中止 | — | 提交人满意度评价【推测】 | 管理报表列、「答复满意度」页签【确认】 |

真实详情页日志的顺序（人员已替换为虚构）：

1. 提交
2. 分拣岗「指派答复人」
3. 处理岗「答复」，备注：`采纳结果:采纳；解决方式:业务科技协同解决（需求项）；答复意见:采纳；优先级:三级（非常用功能影响中等或小）；需求项编号:I20260814-0196；计划落实时间:2026-10-17；`
4. 「通过」，备注：`需求项编号：I20260814-0196,已联动BRDM。`
5. 状态变为「待跟进」

详情日志里，指派答复人和审核通过可以是同一人。这只说明当时那条记录的操作者相同，不能据此把两个岗位合成一个。【确认】分拣岗、处理岗、审核岗是三个独立权限，分拣岗不兼任审核岗。

## 4. 路由规则

【确认】

1. **分行员工提交的建议先进入「待审批」**，由本行分行科技审核岗审批。审批通过后按第 3、4 条自动分配。原演示版的「待处理」已改名为「待审批」。
2. **总行员工（业务研发中心等）提交的建议直接进入平台，不需要审批。**
3. **按平台的产品分类自动分配。** 产品在「产品维护」中归属哪个研发部室、哪条产品线，建议就分配到该部室该产品线的分拣岗，进入「待分拣」。分配看的是提交时选择的「产品名称」，不是提交人自己的部门。
4. **没有产品分类的产品，默认分配到用户体验部的分拣岗统一处理。** 平台本身归用户体验部管理。
5. **研发一体化问题在分配时直接进入 e键通。** 不先到产品部门，也不由分拣岗再转一次。
6. **该部门的分拣岗分配负责人。** 分拣岗把建议分给处理岗。处理岗就是这条建议的答复人。
7. **处理岗答复之后，必须由该部门的审核岗审批。** 采纳和不采纳都要审，不能答复完就结束。
8. **审核不通过，退回给答复人。** 答复人可以改答复后再送审，也可以把建议退回给提出人。
9. **审核通过后，提交人能看到这条建议的处理情况**（是否采纳，以及采纳后的去向）。
10. **从用户声音转来的建议不经过审批，** 来源固定为「客户：用户声音智能分析」，按第 3、4 条自动分配。一次点击生成一条。弹窗字段见《用户声音分析智能体》第 5 节。

演示版的做法：

- 产品分类取「产品维护」中的所属业研部门和产品线。演示数据里「远程银行」「网点排队叫号」两个产品没有分类，用来演示第 4 条。
- 自动分配在操作日志中记为「系统 · 自动分配」，并写明分到的部室和产品线；转 e键通的记为「系统 · 转e键通」。
- 「待审批」列表可批量审批通过、退回提交人、中止或删除，沿用原「待处理」的四个按钮。
- 分行员工提交的研发一体化问题，也先经分行审批，审批通过后再转 e键通【推测】。

【待定】

1. 不采纳在审核通过后是直接「已完成」，还是还有提交人确认。
2. 科技自主解决、需求整合、需求项、创意需求、业务自主解决，在审核通过之后的状态是否仍按第 3.2 节。表内去向来自流程图，审核必经已经确认，去向落地状态仍待核对。
3. 要客建议是否仍由单独的「产品线审核岗（要客）」审批。
4. 答复人退回提出人之后，提出人是在现有的「待修改」里改完再提交，还是另有状态名。
5. 分行审批不同意时，是退回提交人修改还是直接中止。演示版两种都可以操作。

  - 手机APP：个人手机银行、企业手机银行、工银e生活、商户之家、数字货币、境外个人手机银行、工银e办公、兴农通
  - 电脑端：个人网上银行、企业网上银行、工银e办公
  - 微信：微信小程序、微信公众号/服务号
  - 线下：智能柜员机、柜面、POS、ATM
  - 其他：短信银行、电话银行、第三方渠道、行内系统/产品
- **上传附件**：最多 9 张图片，支持截图粘贴。

**选项取值**：

| 字段 | 取值 | 依据 |
| --- | --- | --- |

## 9. 与其他模块的联动

- **产品维护**：产品 → 业研部门 / 产品线 / 业务部门 / 外部机构，决定路由与研发一体化判定。
- **人员维护**：岗位及数据范围决定由谁处理（分拣岗、处理岗、审核岗、要客审核岗、总行业务部门处理岗、分行科技审核岗）。
- **节假日**：停留时长、逾期、平均处理时长都按工作日计算。
- **定时任务与邮件记录**：「优化建议待办提醒邮件」在工作日给当前处理人发 dealSuggestion 提醒。
- **体验问题维护**：
  - 「相似度」开启时，提交前提示相似建议。
  - 「沟通业务部门」开启时，答复环节可转总行业务部门【推测】。
- **字典维护**：来源、分类、影响程度、渠道、解决方式、优先级、未采纳原因可在字典中维护。
- **用户声音**：人工在看板上点一次「转优化建议」，生成一条来源为「客户：用户声音智能分析」的建议，不经审批，按产品分类自动分配到分拣岗。字段见《用户声音分析智能体》第 5 节。演示版从「声音看板 · 功能监测」转入，来源名称已按该节修改。

## 10. 仍待确认的问题

已确认、不再作为开放问题的内容：分行员工提交先进入「待审批」，总行员工提交直接进入平台；按产品分类自动分配到对应研发部室的分拣岗，没有分类的产品由用户体验部分拣岗统一处理；研发一体化问题进入 e键通；其余提交先到产品对应部门；分拣岗、处理岗、审核岗三者权限独立；答复后无论是否采纳都要该部门审核岗审批；审核不通过退回答复人；答复人可以退回提出人；审核通过后提交人可见处理情况。详见第 4 节。声音严重等级的三级标准见《用户声音分析智能体》第 3.6 节。

仍待定：

1. 不采纳在审核通过后的状态名。五种采纳去向在审核通过后的状态，以及「已纳入需求整合池 / e企创」是否算办结。
2. 要客建议是否仍走单独的审核岗。
3. 答复人退回提出人后的状态名是不是「待修改」。
4. 分行审批不同意时退回修改还是中止；分行提交的研发一体化问题是否也要先审批。
5. 影响程度、未采纳原因的完整选项。优先级三级标准已确认，字段文案是否与声音严重等级逐字相同仍可核对。
6. 逾期处理的时限规则。
7. 答复满意度由谁评价，是否超期自动办结。
8. 新增页、待修改页的真实路由。统计视图已有整体视图和产品维度，统计口径是否与优化建议报表共用仍待定。

## 11. 智能化切入点

演示版中的 AI 都是浏览器内的规则模拟，不调用模型；正式环境由行内大模型平台按「智能体管理」中的提示词完成。AI 只给建议并注明依据，由人确认后才写入流程，日志中记为「AI 建议 · 人工确认」。

| 环节 | 思路 | 演示版 |
| --- | --- | --- |
